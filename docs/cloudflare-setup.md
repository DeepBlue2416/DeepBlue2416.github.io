# Cloudflare + домен appleitochka.ru — настройка под нашу архитектуру

## Сначала — важное про архитектуру (иначе половина чек-листа применяется зря)

Наш стек: **статический сайт на GitHub Pages** (фронтенд) + **Cloudflare Worker**
(бэкенд: заявки в Telegram, CRM API, отзывы). **Своего сервера (VPS/Nginx) нет.**

Из этого следует прямой ответ на твой раздел про «сокрытие реального IP»:

- **Скрывать нечего — своего origin-IP не существует.** GitHub Pages отдаётся из сети
  Fastly (их IP, не твои), Worker исполняется на самом эдже Cloudflare (у него в принципе
  нет «origin»). Утечки IP бэкенда, от которой защищают UFW/iptables/Cloudflare Tunnel,
  здесь физически нет.
- Поэтому пункты про **UFW/iptables/Security Groups, Cloudflare Tunnel (cloudflared),
  Origin CA сертификат на Nginx/Apache/Caddy** к текущему стеку **не применяются**. Они
  нужны, только если ты переедешь на собственный VPS — на этот случай оставил приложение
  в конце (Раздел B).

Ниже — Раздел A: что реально нужно настроить сейчас. Раздел B: хардненинг VPS на будущее.
Раздел C: интеграция отзывов Яндекс/2ГИС.

# Раздел A. Настройка Cloudflare для GitHub Pages + Worker

## A1. DNS-записи (вкладка DNS → Records)

Для apex-домена `appleitochka.ru`, указывающего на GitHub Pages:

```
Type  Name              Content                     Proxy
A     appleitochka.ru   185.199.108.153             (см. п.A3 про облако)
A     appleitochka.ru   185.199.109.153             см. A3
A     appleitochka.ru   185.199.110.153             см. A3
A     appleitochka.ru   185.199.111.153             см. A3
AAAA  appleitochka.ru   2606:50c0:8000::153         см. A3
AAAA  appleitochka.ru   2606:50c0:8001::153         см. A3
AAAA  appleitochka.ru   2606:50c0:8002::153         см. A3
AAAA  appleitochka.ru   2606:50c0:8003::153         см. A3
CNAME www               deepblue2416.github.io      Proxied
```

(IP-адреса GitHub Pages стабильны; проверь актуальность в доке GitHub Pages «Managing a
custom domain».) Worker подключается отдельно (п. A5) — под него DNS вручную не создаём.

## A2. GitHub Pages: привязка домена
1. В репозитории → Settings → Pages → Custom domain → `appleitochka.ru` → Save.
   (В сборку уже добавлен файл `public/CNAME` с этим доменом — он попадёт в `dist`.)
2. Дождись, пока GitHub выпустит TLS-сертификат для домена, затем включи **Enforce HTTPS**.

## A3. Тонкость проксирования GitHub Pages (частая ошибка)
Чтобы GitHub смог **выпустить** сертификат для домена, во время проверки записи должны
резолвиться напрямую на GitHub. Поэтому:
1. Сначала поставь записи из A1 в режим **DNS only (серое облако)**.
2. Дождись в GitHub Pages статуса выданного сертификата и включи Enforce HTTPS.
3. **После этого** можно вернуть **Proxied (оранжевое облако)** — получишь CDN/кэш/WAF
   Cloudflare поверх Pages. Если оставить оранжевым сразу — GitHub не выпустит сертификат
   и словишь ошибку «certificate not yet created».

## A4. SSL/TLS — только Full (Strict)
Cloudflare → SSL/TLS → Overview → **Full (Strict)**.
- **Flexible — категорически нет** (шифрует только до Cloudflare, дальше открытый HTTP).
- GitHub Pages и Worker оба отдают валидные сертификаты, поэтому Full (Strict) работает
  без Origin CA — генерировать Origin-сертификат **не нужно** (он для своего сервера).
- Дополнительно: SSL/TLS → Edge Certificates → включи **Always Use HTTPS**, **Automatic
  HTTPS Rewrites**, **Min TLS 1.2**, HSTS (после проверки, что всё по HTTPS).

## A5. Worker на своём поддомене (чтобы фронт не ходил на *.workers.dev)
1. Cloudflare → Workers & Pages → твой Worker → Settings → **Domains & Routes** →
   **Add Custom Domain** → `api.appleitochka.ru`. Cloudflare сам создаст запись и
   сертификат; origin-IP не задействуется (Worker живёт на эдже).
2. В `src/js/config.js` поменяй `apiBase`:
   ```js
   apiBase: "https://api.appleitochka.ru",
   ```
   (Сейчас стоит `*.workers.dev` — оставь до момента, когда домен Worker'а заработает,
   потом переключи. Так фронт обращается к проксируемому домену, а не к IP/служебному
   адресу — это твой пункт 4 «изоляция фронтенда».)
3. CORS уже настроен: в `worker/wrangler.toml` → `ALLOWED_ORIGINS` добавлены
   `https://appleitochka.ru` и `https://www.appleitochka.ru`. После правки — `wrangler deploy`.
4. Turnstile: в панели Cloudflare Turnstile добавь `appleitochka.ru` в список доменов
   виджета (иначе капча на боевом домене не пройдёт).

## A6. Кэш (опционально, ускорение)
Cloudflare → Rules → Cache Rules: кэшировать статику (`*.webp, *.css, *.js, *.svg`)
надолго; для `/*api*` и `product.html`/`index.html` — не кэшировать HTML агрессивно
(или Bypass), чтобы цены/каталог не «залипали». `/api/products` уже отдаёт `no-store`.

# Раздел B. Хардненинг СВОЕГО сервера (только если переедешь на VPS)

Не нужно для текущего стека. Пригодится, если вынесешь бэкенд на VPS с Nginx.

**B1. Фаервол — пускать только Cloudflare.** Закрой 80/443 для всех, кроме диапазонов CF
(https://www.cloudflare.com/ips/). Пример UFW:
```bash
# Сбросить и запретить входящее по умолчанию
sudo ufw default deny incoming
sudo ufw allow 22/tcp                       # SSH (лучше — только со своего IP)
# Разрешить 443 только с диапазонов Cloudflare (пример; подставь актуальные из ips-v4)
for ip in $(curl -s https://www.cloudflare.com/ips-v4); do sudo ufw allow from $ip to any port 443 proto tcp; done
for ip in $(curl -s https://www.cloudflare.com/ips-v6); do sudo ufw allow from $ip to any port 443 proto tcp; done
sudo ufw enable
```
Чтобы в логах origin видел реальные IP клиентов, включи Nginx `set_real_ip_from` для
диапазонов CF + `real_ip_header CF-Connecting-IP`.

**B2. Cloudflare Tunnel (полностью закрыть порты).** Радикальнее фаервола: `cloudflared`
делает исходящее соединение к CF, входящие 80/443 на сервере можно **вообще закрыть**.
```bash
cloudflared tunnel login
cloudflared tunnel create appleitochka
# config.yml: ingress → hostname appleitochka.ru → service http://localhost:8080
cloudflared tunnel route dns appleitochka appleitochka.ru
cloudflared tunnel run appleitochka
```
После этого A-записи на IP сервера не нужны (маршрут идёт через туннель) — IP не светится нигде.

**B3. Origin CA + Full (Strict).** Для своего Nginx: Cloudflare → SSL/TLS → Origin Server →
Create Certificate → положи cert/key на сервер, пропиши в Nginx `ssl_certificate`/`ssl_certificate_key`,
и держи режим **Full (Strict)**. Тогда канал CF↔origin шифрован и проверяется.

# Раздел C. Предотвращение утечки IP через DNS/почту (проверка для любого стека)

- **Серые облака.** Пройди по всем A/AAAA/CNAME: ни один поддомен (staging, dev, cpanel,
  webmail, ftp, `direct.`) не должен «серым облаком» указывать на реальный IP бэкенда.
  У нас реальных origin-IP нет, но правило соблюдай, если заведёшь что-то своё.
- **Старые записи.** Удали исторические A-записи, оставшиеся от прошлого хостинга/парковки —
  они частая причина деанона IP.
- **Почта.** Транзакционные письма (если появятся) шли через внешний API — **Resend,
  Mailgun, SendGrid**, — а не с origin-сервера: заголовки `Received` / `X-Originating-IP`
  иначе раскрывают IP. У нас лиды уходят в Telegram, почтового сервера нет → MX не нужен.
  Если добавишь MX, он указывает на почтового провайдера, а не на веб-сервер.
- **Проверка деанона:** прогони домен через сервисы вроде securitytrails/crimeflare-подобные
  (история DNS) и `dig +short appleitochka.ru any` — убедись, что наружу торчит только CF.

### Чек-лист твоих 4 пунктов → что делать в нашем случае
| Пункт | Наш стек | Действие |
|---|---|---|
| 1. Скрыть IP / фаервол / Tunnel | origin-IP нет | N/A сейчас; Раздел B при переезде на VPS |
| 2. Full (Strict) + Origin CA | нет своего origin | Поставить **Full (Strict)** (A4); Origin CA не нужен |
| 3. Утечки через DNS/почту | почты нет | Проверить серые облака и старые записи (Раздел C) |
| 4. Фронт на проксируемый домен | да | `apiBase → https://api.appleitochka.ru` (A5) |

# Раздел D. Интеграция отзывов Яндекс и 2ГИС

**Честно про «API».** Публичного REST-API, который отдаёт тексты отзывов организации,
у Яндекс.Карт **нет**; у 2ГИС общедоступного API отзывов тоже нет (только партнёрский
кабинет для владельца профиля). Парсить их со статичного сайта нельзя (против правил и
ломается). Поэтому есть два рабочих пути, оба уже поддержаны в коде:

### Путь 1 (рекомендую) — официальные виджеты (всегда актуальны, без парсинга)
- **Яндекс:** Яндекс Бизнес → карточка организации → «Виджеты» → «Отзывы» → скопируй URL
  из `<iframe src="…">`.
- **2ГИС:** кабинет для бизнеса → виджет отзывов/оценок → URL из iframe.
- Вставь их в `src/js/config.js`:
  ```js
  reviews: { sources: [
    { name: "Яндекс Карты", widgetUrl: "https://yandex.ru/maps-reviews-widget/…" },
    { name: "2ГИС",          widgetUrl: "https://widgets.2gis.com/…" },
  ]}
  ```
  Если `widgetUrl` задан — блок «О нас пишут» показывает официальный iframe площадки
  (живые отзывы). Ничего больше делать не нужно.

### Путь 2 — витрина через Worker + редактор в CRM (свой дизайн карточек)
Добавлен API в Worker:
- `GET /api/reviews` — публично отдаёт витрину (кэш из KV).
- `POST /api/admin/reviews` — под `ADMIN_TOKEN`, обновляет её.

**Проще всего — вкладка «Отзывы» в CRM (`/admin.html`).** Там визуальный редактор:
источники (Яндекс/2ГИС), рейтинг, число отзывов, ссылка, поле «Виджет» и избранные
отзывы (автор/дата/оценка/текст) с добавлением-удалением. Кнопка «Сохранить отзывы»
пишет в KV через `POST /api/admin/reviews`, сайт подхватывает при следующей загрузке
(без пересборки). Это и есть «настройка отзывов через API» под ключ.

Фронт (`renderReviews`) сначала пробует `GET {apiBase}/api/reviews`, а если пусто —
берёт `CONFIG.reviews`. Обновить витрину и вручную (curl), без пересборки сайта:
```bash
curl -X POST https://api.appleitochka.ru/api/admin/reviews \
  -H "Authorization: Bearer <ADMIN_TOKEN>" -H "Content-Type: application/json" \
  -d '{"sources":[
    {"name":"Яндекс Карты","url":"https://yandex.ru/maps/org/…","rating":"5,0","count":"120 отзывов",
     "featured":[{"author":"Юлия С.","date":"18 июня","rating":5,"text":"…"}]},
    {"name":"2ГИС","url":"https://2gis.ru/…","rating":"4,9","count":"60 отзывов","featured":[…]}
  ]}'
```
Если захочешь **автообновление** рейтинга/числа — это делается Cron-триггером Worker,
который тянет данные из твоего партнёрского источника (там, где он у тебя есть) и кладёт
в KV. Голый парсинг Яндекс/2ГИС не закладывай — нестабильно и против правил; для «живых»
отзывов используй Путь 1 (виджеты).

# Раздел E. Как обновляются пререндер-страницы /p/<id>/ (свежесть цен)

Пререндер-страницы генерируются на сборке — их статичный HTML это «снимок» цен на момент
деплоя. Важно понимать два уровня свежести:

1. **Пользователь всегда видит актуальную цену.** При открытии карточки `product.js`
   подтягивает каталог из KV (`/api/products`) и «оживляет» страницу — цена/наличие
   обновляются на лету. Отдельная пересборка ради пользователя НЕ нужна.
2. **Бот читает статичный HTML** (снимок). Чтобы и он видел свежие цены — сайт нужно
   пересобрать. Сделано два механизма (оба уже в коде):
   - **Авто-пересборка по правке в CRM.** После «Сохранить» в CRM воркер шлёт в GitHub
     `repository_dispatch` (event `catalog-updated`) → workflow пересобирает сайт. Включается
     заданием секретов воркера `GH_DISPATCH_TOKEN` (fine-grained PAT, Actions: R/W) и
     `GH_REPO` (`owner/repo`). Не задашь — просто не будет авто-пересборки.
   - **Ночная пересборка по расписанию** (`schedule: cron 0 2 * * *` в deploy.yml) — страховка,
     без каких-либо токенов.

Оптимальный режим: включить оба. Тогда правки цен из CRM попадают и в пререндер (для ботов)
почти сразу, а ночной прогон гарантирует свежесть, даже если токен не настроен. Полная
пересборка 227 страниц — это чистый Node, доли секунды; отдельного «инкрементального»
обновления не требуется. (Альтернатива по-максимуму — рендерить /p/* прямо на воркере из
KV, всегда живьё без пересборки; но это заметно сложнее и текущему трафику не нужно.)

# Раздел F. Как передать Google и Яндексу цены и наличие

Пререндер + JSON-LD — это способ №1 (органическая выдача). Но для цен есть и специальные,
«прямые» каналы — товарные фиды. Используй их вместе, они не взаимоисключающие.

**Что уже генерируется на сборке (в dist/):**
- `https://appleitochka.ru/feed-yandex.yml` — YML (Yandex Market Language), 221 товар с ценой.
- `https://appleitochka.ru/feed-google.xml` — RSS-фид для Google Merchant Center.
Фиды пересобираются тем же механизмом, что и пререндер (правка в CRM → repository_dispatch,
плюс ночной прогон), так что цены в них свежие.

**Полный список каналов «цена → поисковик»:**

1. **On-page структурированные данные (JSON-LD Product/Offer)** — уже на каждой карточке.
   Влияет на органические сниппеты Google и колдунщики Яндекса. Основа, но не «магазинный» фид.

2. **Google Merchant Center** (google.com/merchants) — заведи аккаунт, в разделе «Товары →
   Фиды» добавь запланированный фид с URL `…/feed-google.xml`. Даёт бесплатные карточки товаров
   в Google и вкладку Shopping. Обновление — по расписанию Merchant Center (например, раз в день).

3. **Яндекс Вебмастер → «Товары и цены»** (webmaster.yandex.ru) — загрузи YML `…/feed-yandex.yml`.
   Тогда в поиске Яндекса у сайта появляются цены/карточки. Требует подтверждённых прав на сайт.

4. **Яндекс Бизнес** (business.yandex.ru) — карточка организации: там отдельно можно вести
   товары/услуги и цены (показываются в Картах/Поиске по компании). Хорошо для локального спроса.

5. **Яндекс Маркет** (market.yandex.ru, партнёрский кабинет) — если пойдёшь в Маркет как продавец,
   туда грузится тот же YML. Это уже маркетплейс (комиссии, модерация), не только «передать цену».

6. **Sitemap + быстрый реобход** — sitemap.xml уже отдаётся; в Вебмастере и Search Console можно
   ускорять переобход изменённых страниц.

Практический минимум для тебя: подключить `feed-google.xml` в Merchant Center и `feed-yandex.yml`
в Яндекс Вебмастере («Товары и цены»), плюс уже работающие JSON-LD/пререндер. Этого достаточно,
чтобы обе системы видели актуальные цену и наличие.
